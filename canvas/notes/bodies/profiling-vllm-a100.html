The question I started with

While learning how vLLM schedules requests, I became interested in the tradeoffs behind cache reuse:

When does reusing cached work reduce latency, and when does the overhead outweigh the savings?

KV caching saves attention information from tokens the model has already processed. Prefix caching lets requests reuse that information when their prompts begin with the same tokens.

I wanted to understand where that reuse pays off, where it adds overhead, and what determines the boundary between the two. I started experimenting to measure those tradeoffs.

First, a few simple definitions

I measured three main things:

  • Throughput: how many output tokens the server produces per second.
  • Time to first token: how long a request waits before receiving its first output token.
  • Total latency: how long the complete request takes.

I also measured p95 latency, the time within which 95% of requests finish. It helps show what slower requests experience.

Concurrency means the number of requests the client keeps active at once.

More cache reuse brought extra costs

My early experiments changed how cached KV data was reused and managed.

Some changes reused more tokens. But the NVIDIA benchmarks did not establish a throughput improvement from those cache policies. Partial-prefix reuse also increased first-token latency in the tested workloads.

Reusing cached work has its own costs. The server may need to:

  • Look up matching entries.
  • Update cache information.
  • Copy data into a usable location.
  • Manage blocks as requests arrive and finish.

Those costs can consume the time saved by avoiding computation. That led me to profile the system: measure where it was spending time.

Profiling exposed another source of overhead

The profiles showed query and output tensor copies inside a FlashAttention-2 attention path used for single-query work, including decoding.

These were attention-layout copies, separate from copying KV-cache blocks.

This path rearranges query heads into groups before running attention. That arrangement is intended to help computation, but rearranging tensors can also require copies.

I tested a guarded routing change for eligible single-query calls. The guard keeps an explicit “no future tokens” window setting, selecting an existing alternative FA2 path instead of the grouping path. The model’s query heads still share KV heads. Direct native attention checks showed the CPU-recorded clone count falling from two to zero for the tested call.

The next question was whether this would improve complete request performance.

I tested beyond the original setup

Earlier controlled tests used synthetic prompts and eager execution. To broaden the evaluation, I added:

  • CUDA graphs enabled.
  • HTTP serving.
  • Human-written prompts from WildChat.
  • An additional model family.

Models and workloads

For this final benchmark, all experimental cache policies were disabled; native prefix caching and chunked prefill remained enabled. This isolates the attention-routing change from the earlier cache experiments.

Requests used local HTTP, with the client and server on the same machine. Timings included HTTP streaming and detokenization, but excluded tokenization, model loading, compilation, and warmup. These measurements are not internet-facing application latency.

The prompts were English and mostly short. KV memory was ample, and no preemptions occurred, so these results do not establish benefits under memory pressure or predominantly long-prompt traffic.

The models were:

  • Qwen3–0.6B: 0.6 billion parameters.
  • Qwen3–1.7B: 1.7 billion parameters.
  • SmolLM3–3B: 3 billion parameters.

Each model used the same 96 selected human prompts, rendered with its own chat template. I tested concurrency three and sixteen, with fixed output lengths of 32 and 128 tokens.

Each comparison used six paired repeats. Stock and optimized servers ran separately, with their order alternating across repeats.

The complete timed study included 36 fresh servers, 13,824 requests, and 1,105,920 generated tokens.

This was a controlled workload using real prompts. It was not a replay of production traffic: output lengths were forced, and requests followed a fixed concurrency limit.

Correctness checks set an important boundary

Before accepting speed results, I checked numerical results and generated outputs.

All three models passed the checks in batch-invariant FA2 mode with CUDA graphs enabled. Batch-invariant mode is intended to keep model results consistent when requests are batched differently.

In that mode:

  • Across all three models, all 96 checked pairs of full API log-probability vectors matched in value.
  • Across all three models, all 24 checked natural-response pairs produced identical token sequences.
  • Every timed output sequence matched across variants and repeats.

The default BF16 comparisons exceeded my declared numerical-equivalence limits, so I excluded those modes from timing.

This does not establish that their answers were worse. Different generated text is not an accuracy score. It means I could not claim numerical equivalence under the checks I had defined.

The performance results below therefore apply to the validated batch-invariant configuration.

The speedup depended on concurrency

At concurrency three

The throughput improvement was small and repeatable:

  • Qwen3–0.6B: about 2.9–3.2%.
  • Qwen3–1.7B: about 1.8–2.0%.
  • SmolLM3–3B: about 1.8–2.0%.

Across these low-concurrency settings, p95 total latency fell by approximately 1.5–2.8%.

At concurrency sixteen

The benefit largely disappeared. Most throughput comparisons did not establish an improvement.

SmolLM3 with 128-token outputs showed a small, repeatable throughput regression of approximately 0.63%.

Qwen3–0.6B with 128-token outputs also showed approximately 0.76% worse p95 total latency.

Time to first token also showed no consistent improvement across the study.

The result was useful, but clearly conditional.

Attention routing with CUDA graphs and human prompts. Reported improvements are median paired changes across six repeats; error bars show 95% bootstrap intervals. Intervals crossing zero do not establish a consistent improvement.

The routing change affected more than copies

Further source inspection clarified an important part of the experiment.

The routing change also affects automatic split-KV execution in the frozen FA2 implementation. Split-KV divides attention work across portions of the cached keys and values. Changing that choice can affect parallelism and floating-point reduction order.

Batch-invariant mode already forces a single split in the pinned backend. That helps explain why execution mode matters to this experiment.

The study measured a routing change with several connected effects. It did not isolate every part of the speed difference as a pure copying cost.

What I can conclude

The strongest conclusion is:

A guarded attention-routing change improved throughput by roughly 1.8–3.2% at low concurrency in the tested batch-invariant FA2 configuration. The benefit mostly disappeared at higher concurrency.

The experiments also changed how I think about optimization:

  • Saving computation is useful only after accounting for the cost of reuse.
  • Removing copies can change other execution choices.
  • A speed improvement needs numerical and output checks.
  • Neutral results and regressions help define where an optimization is useful.

I also found closely related prior work, including a 2024 output-buffer workaround and an output-stride proposal addressing the same decode path. This study does not establish a new attention algorithm.

What I would investigate next

A useful next experiment would try to reduce layout copies while preserving the grouped attention and split-KV choices. That would help separate the cost of moving data from the benefit of the existing computation path.

I would also expand task-level quality evaluation, workloads, and hardware coverage before making a broader deployment claim.

For now, the value of this experiment is a measured boundary: a small optimization helped in a specific setting, and broader testing showed where that benefit stopped.
