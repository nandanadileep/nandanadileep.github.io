Every time you start a new LLM-powered project, you face the same fork in the road: do I prompt it, build a retrieval pipeline around it, or fine-tune a model? Pick wrong and you either waste weeks (or tokens hehe) over engineering something that a good system prompt could’ve handled, or you ship a brittle prompt-hack that falls apart the moment inputs get messy.

I am going to walk you through one project per approach; what the problem was, why I picked that approach, and what would’ve gone wrong if I’d picked differently.

Prompt Engineering: AI Code Review Bot

I built a GitHub App that automatically reviews pull requests. When someone opens or updates a PR, the bot grabs the diff, sends it to Llama3–8B via Groq, and posts a structured review comment right on the PR flagging bugs, security risks, and code quality issues.

I didn’t fine-tune anything. I didn’t build a vector store of past code reviews. I wrote a prompt.

Why? Because the model already knew how to read code and reason about it. Llama3–8B has seen enough code during pretraining that it can spot a missing null check or an exposed API key without me teaching it what those are. The gap wasn’t knowledge or behavior, it was direction. The model needed to know: what is the diff, what should you look for, and how should you structure the output.

That’s the core of prompt engineering, you’re not adding new capability to the model. You’re steering capability it already has. In my case, the prompt set the role (you’re a senior code reviewer), defined the scope (focus on bugs, security, readability), injected the context (the actual PR diff), and specified the output structure.

If I had gone the RAG route, I’d have been building a retrieval pipeline for no reason, the model didn’t need external knowledge to review a diff sitting right in the prompt. If I had fine-tuned, I’d have spent days curating code review examples and training a model to do something it could already do out of the box with the right instructions.

RAG: Chatting With Your Documents (Without LangChain)

Next project, different problem. I built a document chat system from scratch, no LangChain, or any other framework. Upload your docs, ask questions in natural language, get answers grounded in the actual content. The stack: sliding window chunking, FAISS for vector search, and a React frontend.

This time, prompting alone wouldn’t cut it. Not because the model lacked the ability to answer questions, it’s great at that. The problem was that the model had never seen my documents. You can’t stuff a 200-page PDF into a prompt and call it a day. Context windows have limits, and even if they didn’t, throwing an entire document at a model and hoping it finds the right paragraph is wasteful and unreliable.

I deliberately skipped LangChain because I wanted to understand every layer of the RAG pipeline myself. When you hide behind abstractions, you lose the ability to debug, optimize, and explain what’s actually happening.

So the answer was retrieval. When a user asks a question, the system first searches for the most relevant chunks using vector similarity (FAISS), then feeds only those chunks into the prompt alongside the question. The model’s job isn’t to know the answer from training, it’s to synthesize an answer from the retrieved context.

This is what RAG solves: the model has the skill (reading comprehension, summarization, reasoning) but lacks the knowledge (your specific documents). Instead of baking that knowledge into the model through fine-tuning, which would be expensive, brittle, and outdated the moment the documents change, you retrieve it at inference time.

Fine-Tuning: Teaching a Model to Play Chess

Last one completely different problem. I fine-tuned Gemma3 on chess notation to predict valid moves and understand board states.

If you were gonna try prompting your way through this one, tell an LLM “given the moves e4 e5 Nf3 Nc6, predict the next move.” It might give you something plausible. It might also give you an illegal move and sound confident about it. LLMs don’t understand chess (at least smaller models like the one I am using) , they’ve seen chess games in their training but they haven’t learned the structure of the game. They’re pattern-matching on text, not reasoning about board state.

RAG doesn’t help either. There’s no document to retrieve. You’re not asking “what does Wikipedia say about the Sicilian Defense”, you’re asking the model to internalize the rules and patterns of chess deeply enough to predict what comes next in a sequence of algebraic notation. That’s not a knowledge retrieval problem. That’s a behavior problem.

So I fine-tuned. I trained Gemma3 on chess game data, sequences of moves with the task of predicting the next valid move. After training, the model didn’t need instructions or retrieved context. It had internalized the patterns of chess notation well enough to produce legal, strategically reasonable moves on its own.

This is the clearest signal for fine-tuning: when you need the model to develop a capability it fundamentally doesn’t have. Not knowledge it can look up. Not instructions you can write. An actual new behavior baked into the weights.

The tradeoff is real though. Fine-tuning costs compute, requires good training data, and the moment your target behavior changes, you retrain. I used LoRA (which freezes the base model and only trains a small set of adapter weights) to keep it manageable. But even with parameter-efficient methods, it’s still the heaviest tool in the box. That’s why it comes last in the decision tree, not first.

The tradeoffs show up quickly in production. Prompting is cheapest and fastest, but brittle when inputs shift. RAG adds latency and token cost due to retrieval and longer context, and it fails when the right chunks aren’t found. Fine-tuning reduces prompt complexity at inference, but costs upfront in data and training, and can overfit if your data is narrow. Each fails differently: prompts break silently, RAG misses context, fine-tuned models fail confidently. So the real decision isn’t just what works, it’s what fails in a way you can tolerate.

So next time you start an LLM project, ask three questions in order:

Does the model already know how to do this? → Prompt it.

Does it know how but lacks specific knowledge? → RAG.

Does it need to consistently behave differently than its base personality? → Fine-tune.

In reality, you’ll probably use all three. These aren’t mutually exclusive. Production systems layer them, a fine-tuned base model, a RAG pipeline for live knowledge, and a well-crafted prompt holding it all together. The framework isn’t about picking one forever. It’s about knowing the minimum viable approach and layering up only when you need to.
