Hallucination Cascade

Did the agent lie about what it knew?

An agent fabricates a fact (eg: claims a tool returned data that it never actually called), then uses that fabrication as the basis for subsequent decisions. Each downstream action compounds the error, creating a chain reaction where wrong conclusions are built on false premises. The agent’s confidence remains high because it has no feedback signal that the initial assertion was unfounded.

Every factual assertion the agent makes during reasoning must be traceable to a tool call and its result. Implement a verification layer that, before any action is taken on a claim, confirms a corresponding tool_use + tool_result pair exists in the trace. Claims with no tool backing should be flagged and blocked from influencing downstream decisions.

Observability Black Hole

Did the agent fail to see what happened?

An agent performs an action (calls a tool, sends data, modifies state) but cannot observe whether the action succeeded or failed. The agent has no feedback loop no response, error message, or verification query so it proceeds based on assumption. It declares success without confirmation, or worse, repeats the same failed action multiple times because it has no signal that it’s failing.

Pair every write tool with a mandatory verification tool call before the agent is allowed to proceed. Define explicit completion criteria for every task at the start of execution, and require the agent to check each criterion against tool results before it is allowed to give a final response.

Infinite Reasoning Loops

Did the agent get stuck going nowhere?

An agent cycles through the same reasoning pattern, decision, or action repeatedly without progress or variation. It retries the same failed tool call identically, re-reads the same documentation looking for missed detail, or oscillates between two contradictory conclusions. Token count grows linearly while the agent makes no forward progress toward the goal.

Implement loop detection at the executor level, not in the agent’s reasoning, the agent will not recognize it is stuck. Hash the last N action sequences at each step; if the same hash recurs within a sliding window, halt execution automatically and surface the loop to the user. Set hard token budgets and distinct tool call ceilings per task. The agent should never be given the option to continue indefinitely. For oscillation between contradictory conclusions specifically, introduce a forced commitment rule, after two visits to the same decision point with no new tool evidence, the agent must either call a new tool to break the tie or escalate to the user rather than re-reasoning over the same data.

Tool Misuse / Boundary Violations

Did the agent act correctly?

An agent calls tools in the wrong order, with the wrong scope, or outside their intended boundaries. It may invoke a destructive tool (DELETE, OVERWRITE, SEND) when a read-only one was appropriate, pass unvalidated output from one tool directly as input to another, or call tools in a dependency order that violates the system’s assumptions.

For example, updating a record before confirming it exists, or sending a notification before the underlying action has committed.

Define preconditions for every mutating tool and enforce them at the tool layer, not in the agent’s reasoning. Similarly, enforce strict input/output schemas at tool boundaries. Output from Tool A should be validated against Tool B’s expected input before the agent is permitted to pass it through.

Goal Misalignment / Task Drift

Did the agent decide to solve the right problem?

An agent begins with the correct objective but gradually optimizes for a proxy goal instead, one that is easier to satisfy but not what was actually asked. It may complete all its tool calls without error, produce a confident final response, and still have solved the wrong problem. The drift is rarely sudden. It accumulates across steps as the agent reframes the task to fit the tools available, the data it found, or the path of least resistance. By the end, the trace looks healthy but the output is misaligned with the original intent.

At task initialization, decompose the instruction into explicit sub-goals and store them as a checklist external to the agent’s context window. At each major decision point, evaluate the agent’s current trajectory against this checklist, not against its most recent reasoning, which may have drifted. Before the agent is permitted to emit a final response, require it to map its output to each sub-goal explicitly. Any sub-goal with no corresponding output should block completion and return the agent to the task, not allow it to declare success.

Context Window Corruption / Memory Poisoning

Was the agent reasoning over bad input?

An agent’s decisions are only as good as the context it is reasoning over. As a long-running agent accumulates tool results, intermediate outputs, and conversation turns, its context window fills with information of varying reliability. Stale data sits alongside fresh data with no timestamp. A failed tool result that was never resolved remains in context and gets treated as valid. An early incorrect assumption, never corrected, gets re-read and reinforced with each new reasoning step. The agent isn’t hallucinating, it is faithfully reasoning over corrupted input.

Treat context as a cache, not a source of truth. Every critical value the agent reads early, resource status, user data, config etc should have an expiry window. If more than N steps have passed since a fetch, re-fetch before acting on it. When a tool call returns an error or null, invalidate that result immediately, it should never enter reasoning as a valid observation. In multi-entity tasks, separate retrieved data by the entity it belongs to so data fetched for one resource cannot bleed into decisions about another. And any value the agent has re-read 2 or more times without a fresh tool call should trigger a forced re-verification before action.

Premature Termination / False Completion

Did the agent actually finish the problem?

An agent declares the task complete before it actually is. It returns a confident final response, stops issuing tool calls, and hands control back to the user, but the goal has only been partially satisfied. This isn’t the agent lying about what it did. It genuinely believes it is done. The failure is in how it evaluates completion: it mistakes the absence of obvious next steps for the presence of a finished result, or it hits a soft signal (a successful tool call, a non-error response) and interprets that as task closure.

Define completion criteria before the agent starts, not after it stops. At task initialization, decompose the instruction into explicit sub-goals and store them as a checklist external to the agent’s reasoning, not inside the context window where they can be quietly dropped. Pair every mutating action with a mandatory verification call: a GET after a CREATE, a test run after a code change, a read-back after a write. Before the agent emits a final response, require it to map its output to each sub-goal. Any sub-goal with no corresponding tool result blocks completion.

Cascading Permission / Trust Escalation

Did the agent stay within the authority?

An agent begins with a defined scope of access and authority. Over the course of execution, it quietly expands that scope, not through explicit grants, but through inference. It reads a successful tool response as implicit permission to do more. It inherits credentials passed through one tool and uses them in another context they were never intended for.

At the start of every task, declare an explicit permission manifest: which tools the agent may call, which resources it may read or write, and which domains it may cross into. This manifest should be enforced at the executor level, tool calls outside the manifest are rejected regardless of how the agent justified them. Credentials and identifiers extracted from tool results should not be automatically reusable in other tool calls.

Instruction Injection / Prompt Hijacking

Did the external content take control?

An agent reads external content as part of its task: a webpage, a document, a database record, an email, and that content contains text designed to look like instructions. Its goal shifts without the user’s knowledge.

The agent must operate with a hard architectural separation between its instruction context (system prompt, user input) and its data context (tool results, fetched documents, retrieved records). Content in the data context should never be parsed for instructions. Implement an input sanitization layer that strips or escapes instruction-like patterns from all external content before it enters the agent’s reasoning context.

Agents fail quietly. They don’t crash with a stack trace, they produce confident output, clean traces, and completed tool calls, and still deliver the wrong result. None of the nine failure modes here require the agent to be broken. They require only that the agent has no mechanism to catch itself. The debugging order in this article starts with what the agent claimed to know, works outward to what it did, and ends with what it was allowed to do. Each layer assumes the ones above it have been cleared. The guardrails follow the same logic, they are not patches on individual failures, they are structural properties that make an entire class of failures impossible rather than merely unlikely. Build the checks in before the agent runs.
