This article is about LlamaIndex OSS, the open source framework, not LlamaParse, their document parsing platform.

You have a conversational agent. Around turn fifteen, it starts forgetting things. Around turn thirty, it contradicts itself. The instinct is to bump the context window from 16K to 128K. It helps for a while. Then the same degradation sets in, just later, at four times the compute cost.

The real problem was never window size. It was treating the context window as infinite scratch paper. There is a four-tier memory architecture sitting inside LlamaIndex that most developers never deliberately use: short-term, long-term, episodic, and procedural. Each tier has a job. Each one breaks in a specific way when ignored.

Short-Term Memory: The Active Queue

The failure mode here is subtle. A 128K context window is not 128K of reliable recall. Pretraining data is overwhelmingly short documents, so the model has learned, at the weight level, to weight early tokens more heavily. Modern LLMs also use Rotary Position Embeddings, where attention between two tokens decays as their relative distance increases. Recent tokens accumulate more attention mass by geometry, not by choice. The result, documented as “lost in the middle,” is that information buried in the center of a long context gets attended to far less than what’s at the start or end.

LlamaIndex’s approach is a FIFO queue with a hard token budget, 70% reserved for raw conversation history and 30% allocated to long-term memory blocks. When the queue fills past a flush threshold, the oldest messages waterfall down into long-term storage. Hard constraints and instructions go at the start of context to benefit from primacy bias. Retrieved episodic content goes immediately before the current message to benefit from recency bias.

The gap is importance scoring. Evicting by age sounds reasonable until a user correction from turn three flushes before a filler “sounds good” from turn forty. Any fixed heuristic fails on edge cases. LLM-based scoring would work but adds latency on every message. LlamaIndex leaves this unsolved, which means in a long conversation, the messages most worth keeping are exactly the ones most likely to disappear.

Long-Term Memory: The Vector Layer

The failure mode is that embeddings are lossy compression in ways that destroy meaning without warning. Negations are the clearest example. “Do not contact before 9am” and “contact before 9am” have surprisingly similar embeddings in many models. The word “not” does not reliably push a vector to a different region of the space. When rolling summarization compresses “do NOT send reminders before 9am,” it often produces “user has preferences about reminder timing” or worse, “user prefers morning reminders.” The negation is gone. The summary looks complete and readable. The constraint has been reversed.

LlamaIndex deals with this using a layered chunking and retrieval pipeline. For chunking, it supports strategies ranging from simple fixed-size splitting to topic boundary detection, where chunks end at actual semantic transitions rather than arbitrary token counts. The most precise approach indexes individual sentences for matching but stores surrounding sentences alongside each one, so the model reads context rather than just the matching fragment. On top of chunking, LlamaIndex implements HyDE: rather than embedding the query directly, it asks the model to write a hypothetical answer first and embeds that. A hypothetical answer already lives in the same part of the embedding space as real document content, closing the gap between how users write queries and how documents are written. The catch is that HyDE fails silently when the model’s hypothesis is wrong, it retrieves from a coherent but incorrect neighborhood, with high similarity scores and no signal that anything went wrong. A cross-encoder reranker paired with HyDE gives a second opinion that is far less vulnerable to a bad initial hypothesis.

The gap is structured extraction. LlamaIndex extracts facts from conversation before archiving them, which is better than storing raw text. But natural language facts are still lossy. A later extraction pass might rephrase a constraint. A summarization step might drop the negation entirely. A truly robust system needs typed schemas — where the NOT is a boolean field, the time is a structured value, and the constraint is a record that cannot be accidentally rephrased away. Without that, you are still trusting language to preserve meaning, which is exactly the failure mode you were trying to escape.

Episodic Memory: Conversation History Across Sessions

The failure mode is treating an append-only log as mutable state. Raw conversation history is a log: each entry is immutable, contradictions accumulate without resolution, and the model must reconstruct state on every inference call by reading all past turns and figuring out what is still current. This works for short histories. At scale, contradictions pile up and the model attends to both the original statement and its correction with roughly equal weight, producing unpredictable output.

LlamaIndex handles this with two complementary strategies. The first embeds flushed conversation turns for semantic retrieval, so when a new session starts, past exchanges relevant to the current topic get pulled back into context. This is how an agent can remember a project you worked on three weeks ago without carrying three weeks of raw history in every window. The second runs an extraction pass before archiving, pulling out discrete facts and updating them when new information contradicts old, pushing the system toward maintaining state rather than just accumulating log entries. What neither strategy handles automatically is tool result bloat. When a tool call returns two thousand tokens of raw JSON, that payload gets archived verbatim. By turn twenty in a tool-heavy agent, raw results can dominate the token budget.

The gap is the decision log pattern. LlamaIndex’s extraction strategies treat all information with roughly equal priority. But not all information ages the same way. A hard constraint like “under no circumstances contact clients on weekends” should be as fresh on turn two hundred as it was on turn two. The naive solution is to never flush these messages, but without a separate store you have no way to distinguish them from ordinary history. An importance classifier could tag them, but then you need the classifier to be reliable enough that a missed tag doesn’t silently drop a hard constraint. LlamaIndex does not implement this. You need a dedicated never-summarized store injected at the highest priority on every turn, and the logic to populate it is entirely yours to build.

Procedural Memory: How the Agent Knows How to Behave

The failure mode is invisible regression. You fine-tune for customer support tone and formatting. The model’s instruction-following on edge cases degrades by 12%. Your eval set covers customer support tasks. You ship the regression and never know it happened. Fine-tuning on any task degrades performance on adjacent tasks that share weight regions. This is not a risk. It is a statistical certainty.

LlamaIndex handles the in-context side with a static memory block: text that is always injected at a fixed position with a fixed priority, never evicted, never summarized. It is the right place for standing instructions and persona definitions. For weight-level adaptation, LlamaIndex defers entirely to external tooling. You train a LoRA adapter using something like HuggingFace PEFT or Unsloth and plug it in through the LLM integration layer. The framework has evaluation utilities for fine-tuned embedding models, but nothing for evaluating regressions in the LLM itself after fine-tuning.

The gap is a capability regression suite. Fine-tuning degrades adjacent capabilities in ways that are invisible unless you measure them. The problem is that “adjacent” is hard to define in advance, you discover which capabilities were affected after you ship, not before. A proper regression suite needs broad coverage across instruction following, refusal behavior, output formats, and tasks that share weight regions with your fine-tune objective. Without it, you are deploying blind.

There is now a map.

Short-term for what the model is actively working with.

Long-term for what needs to survive beyond a single session.

Episodic for what happened and when.

Procedural for how the agent is supposed to behave.

LlamaIndex builds the infrastructure for all four cleanly and deliberately. The gaps it leaves are not oversights, they are the boundary where the framework ends and your system begins. That part is for the users to build. That is also the interesting part.
