Once you move from a single agent to multiple agents, you are no longer just prompting a model. You are designing a system. Messages have to be passed, state has to be shared, and every component needs to agree on what data looks like.
This is where most systems break.
LangChain approaches this problem not by making agents smarter, but by making communication stricter. To understand how multi-agent orchestration actually works, you need to look at the problems it is trying to solve.

Orchestration Patterns

Agents can be coordinated in a few common ways. In hierarchical orchestration, a supervisor breaks the goal into pieces and delegates each to a specialist. In sequential pipelines, agents hand off to each other one step at a time. In ensemble, multiple agents tackle the same problem independently and their outputs are compared. In shared state, all agents read from and write to a common context rather than calling each other directly.

Patterns in LangChain,

Hierarchical is the primary pattern. Each agent is a self-contained unit that can be plugged into a larger graph as a node. A supervisor routes between specialists, each unaware of the others. This keeps agents independently testable and the system easy to extend.
Shared state is not a pattern you choose, it is the default. All agents communicate through a single central state object carrying the full conversation history. Nothing passes values around explicitly. This makes the system inspectable at every step and eliminates hidden data flows.
Sequential is built into every agent’s internal loop. The model runs, tools execute, the model runs again, in that fixed order until there is nothing left to do. Reasoning has dependencies, and keeping the order explicit makes bugs easy to find.
Ensemble is only partially there. Tool calls issued by the model do run in parallel, which is ensemble at a small scale. But full ensemble, multiple agents producing independent answers that get reconciled, is not built in. Aggregation strategies are too application-specific, so the framework leaves that decision to the developer.

Communication Layer Problems

Once you have multiple agents, a new set of problems appears. How does one agent hand something off to another? What form does that handoff take? And what happens when one agent’s output does not quite match what the next agent expects?

The serialization problem

When agents communicate, anything they share has to cross a boundary. It gets saved, passed along, or sent as a message. Because of that, it must be in a format that can be written down and read back later.
LangChain uses structured message objects. Each message has a clear type and format, and the entire interaction is just a list of these messages. There is no hidden memory sharing. If something cannot be serialized, it cannot move between agents.

{
 "type": "ai",
 "id": "msg-abc123",
 "content": "The capital of France is Paris.",
 "tool_calls": [],
 "name": "researcher-agent"
}

The structured communication problem

Plain text is too ambiguous for agents. If one agent sends a sentence and another needs specific fields, something has to extract and validate that data.
LangChain enforces structured output. Agents produce data that follows a predefined schema, and the system validates it before passing it forward. This removes guesswork and makes communication reliable.

State and Context Problems

The context transfer problem
Context is everything that has happened so far, not just the last message. Passing this between agents is difficult because it grows over time and models have limits.
LangChain treats the message list as the single source of truth. Every agent reads from the same shared history. The system may control how much each agent sees, but the format remains consistent. There is no translation between agents.

Interface Problems

The impedance mismatch problem
Agents often expect different data formats. One agent’s output may not match another agent’s input.
LangChain forces every agent to define its input and output schemas in advance. These schemas are checked and merged before the system runs. If they do not align, the system fails early instead of breaking during execution.

Execution Problems

Conflict Resolution
Multi-agent systems do not fail in one single way. Conflicts show up in different forms depending on where they happen, and each type is handled differently.

When multiple tools or agents try to update the same piece of state at the same time, the system applies strict rules. Some fields are appended to, like message history. Others follow a last-writer-wins approach, such as timestamps. Numeric values are accumulated, and nested structures are merged. If two updates are fundamentally incompatible, the system does not guess. It raises an error.

Conflicts can also happen earlier, at the decision stage. If the model generates parallel tool calls that would interfere with each other, the system catches this before execution. Instead of proceeding, it sends an error back into the conversation and asks the model to try again. The model is expected to self-correct.

Not all conflicts are treated as errors. When two agents or tools disagree on a fact, the system does not attempt to resolve it. Both results are stored in the shared message history, and the model sees them together. The responsibility of choosing what to trust is pushed back to the model.

There is a stricter boundary when it comes to output quality. If a model produces something that does not match the expected schema, it is rejected. The validation error is fed back, and the model must regenerate its response. This repeats a few times. If it still fails, the system stops. There is no partial acceptance.

Some conflicts are not allowed to reach execution at all. If schemas cannot be aligned or components expect incompatible data shapes, the system fails during setup. It does not attempt to resolve these issues at runtime.

Multi-agent systems are not just about adding more agents.
They are about designing how those agents communicate.
Most failure points come down to one thing: unclear contracts.
What data is passed, in what format, and who validates it.
