AI memory is no longer a research term. Every major AI provider has now engineered state management systems to make stateless LLMs behave as if they remember you. Many of you might have noticed that the way Claude injects what it knows about you and the way ChatGPT uses that same knowledge feel fundamentally different. (I found Claude weird, for the record.) That makes sense. OpenAI and Anthropic appear to have made fundamentally different architectural bets on how persistent memory should work. They change the security profile, token efficiency, and trust boundary of the entire system.

Every memory system built on top of an LLM is solving the same problem: how do you make a stateless function behave as if it has history? The answer is always the same. You inject context into the prompt. The difference is what you inject, when, and who decides.

ChatGPT’s Memory Evolution: From Notepad to Dreaming V3

April 2024: Saved Memories (V1)

The first version was essentially a notepad. You told it what to remember, it saved a line item. “Remember I’m a bird.” “Remember I prefer worms.” Explicit, manual, and brittle.

The problems were obvious. I remember manually deleting stale memories that had long stopped being relevant. This version also required strong cues to trigger a memory write. The model had to detect an explicit instruction. Anything subtle got dropped.

April 2025: Dreaming V0

This is where it gets architecturally interesting. OpenAI added a background process that could reference broader chat history beyond just the saved memories list. It no longer required explicit user instruction to write a memory.

But V0 was a layer on top of V1, not a replacement. Two systems running simultaneously, which created inconsistencies. Sometimes memory came from the notepad, sometimes from the background synthesis, and the model couldn’t always tell which was more authoritative. OpenAI’s own retrospective framing positions V0 as never sufficient as a standalone system.

June 2026: Dreaming V3

OpenAI’s own June 4 2026 blog post names this system “Dreaming V3” and describes it as their most capable memory architecture yet. It becomes the new default foundation, with saved memories still available as a fallback. A background process learns from many conversations and synthesizes memory state continuously, capturing context that arises naturally rather than waiting for an explicit instruction.

Tenable Research documented this while investigating ChatGPT vulnerabilities in November 2025. They say the synthesized memory state is maintained in a separate data layer and injected into the system prompt at inference time. Every new conversation starts with a context window that already contains what the system has synthesized about you. Memory now self-updates as time passes.

What remains undocumented is the exact mechanism by which synthesis runs, how frequently it triggers, and whether additional retrieval layers operate underneath. The observed behavior suggests synthesized summaries rather than per-conversation retrieval, but OpenAI has not confirmed the internal architecture in detail.

This introduces a compression tradeoff. Whatever the synthesis process decides isn’t worth retaining gets dropped from the active memory state. Whether it’s recoverable in a future synthesis pass is unknown.

The trust boundary argument is where things get structurally important. In traditional software, trust boundaries are enforced by external systems: authentication layers, validation schemas, something outside the data that checks it before it moves between zones. Based on what’s publicly known, this appears to collapse in Dreaming V3. The model decides what to write, the model is exposed to conversation content that could be malicious, and the model later reads and acts on that memory. Neither OpenAI nor external researchers have documented a validation layer sitting between synthesis and injection. That absence is notable, though it is absence of evidence, not confirmed absence of a control.

Claude’s Memory Architecture

Unlike OpenAI, Anthropic has not published a detailed technical breakdown of their memory system. No named architecture, no eval numbers, no public blog post explaining the internals. Most of what’s known comes from reverse engineering, security disclosures, and leaked system prompts.

How It Works

Based on reverse engineering and security research, Claude’s memory appears to operate through a userMemories block injected directly into the system prompt at the start of every conversation. Not a retrieval step. Not a database query. A flat block of synthesized text that arrives before you've said anything.

The approach appears conservative and extractive by design: pulling recognizable facts and patterns from recent conversations rather than synthesizing broadly across your entire archive. The synthesis cadence and exact scope have not been publicly confirmed by Anthropic.

No publicly documented conflict resolution mechanism comparable to OpenAI’s has been identified for Claude. Dreaming V3 explicitly addresses staleness, rewriting memories as circumstances change.

The Injection Point and What It Shares With ChatGPT

Both systems surface memory as privileged context presented before the user’s current message. For ChatGPT, Tenable Research documented this as system prompt injection at inference time. For Claude, security researchers have observed the same pattern via the userMemories block. Both models treat this content as higher trust than anything in the user turn.

Where they diverge is in apparent attack surface. ChatGPT’s background synthesis sweeps broadly across conversation history, meaning a payload buried in a document you processed weeks ago could plausibly surface in persistent memory on a future synthesis pass. Claude’s sweep appears narrower: recent conversations, conservative extraction. Harder to get a payload in, but not impossible.

But narrower is not safe. The moment something lands in userMemories it carries the same elevated authority as anything else in the system prompt. Narrower attack window, same consequence.

At a high level, both systems solve the same problem: how do you make a stateless model behave as if it remembers the user? The answer in both cases is synthesized memory injected into privileged prompt context. The difference lies in how that memory is created, updated, and maintained over time.

OpenAI’s Dreaming V3 appears to treat memory as a continuously evolving state. New conversations are synthesized into an existing memory representation, stale information is rewritten, and memory adapts as circumstances change. The emphasis is on keeping the memory state current, even if that means repeatedly modifying what was previously stored.

Claude’s userMemories system appears to take a more conservative approach. Public observations suggest a narrower synthesis scope and a stronger focus on extracting stable facts and patterns from recent interactions. While Anthropic has not documented the underlying architecture, the resulting behavior feels less like a continuously rewritten memory state and more like a curated profile of user information.

Both systems appear to favor synthesized summary injection over per-conversation retrieval, which keeps injected context leaner than raw chunk retrieval would. But the compression is lossy and opaque. What got dropped from synthesis is invisible to your application. You pay a context cost on every conversation for a memory block you didn’t author and can’t fully inspect.

Neither architecture exposes typed, timestamped, or attributable memory writes to the applications built on top of them. No public documentation from either company describes an external validation layer between synthesis and injection.
