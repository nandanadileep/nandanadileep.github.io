I went through the leaked codebase to understand how this AI system is actually built.

The .npmignore that appears to have shaken the community

On March 31, 2026, a researcher noticed something odd inside a routine update to Anthropic’s Claude Code on npm. A 59.8 MB debug file that wasn’t supposed to be there, and inside it, the entire source code. 512,000 lines of TypeScript. 1,900 files. Every engineering decision Anthropic had made, sitting in plain sight.

The Claude Code runtime appears to use Bun, which generates sourcemap debug files by default. When publishing to npm, the sourcemap files were not excluded, effectively one missing line (*.map) in .npmignore which appears to have exposed everything.

Even though most coverage treated this as a scandal, I am going to look into the internal decisions and design patterns that make this AI system work.

The 5 Layer Architecture

Layer 1 Entrypoints
Claude Code can be accessed in multiple ways — through the terminal, VS Code, browser, desktop apps, or programmatically via an SDK. These are essentially different entry points into the same system. The code for these interfaces lives in src/entrypoints/, and they all eventually hand off control to a shared execution engine (e.g., launchRepl()).

Layer 2 REPL, Hooks, and State
At the core is a REPL (Read–Eval–Print Loop), which powers the interactive session. The CLI bootstraps through a large orchestration file (main.tsx), which parses input, initializes the environment, and starts the loop.

A hook system allows specific parts of the execution flow to be intercepted or modified, while shared state maintains context across the session.

Layer 3 QueryEngine (Conversation Core)
Each conversation is managed by its own QueryEngine. It maintains a single, centralized list of messages representing the entire conversation.

All new inputs go through a controlled interface (submitMessage()), and no other part of the system modifies this message list directly. This enforces a reliable “single source of truth” for the conversation state.

Layer 4 Tools (Execution Layer)
The system uses a collection of tools to perform real actions — such as running shell commands, reading and editing files, searching code, or spawning sub-agents.

This tool-based design is what allows the system to go beyond simple text generation and handle real engineering workflows.

Layer 5 Services (Underlying Infrastructure)
Beneath everything are supporting services like authentication, API communication, memory management, analytics, and integrations (e.g., language servers).

These components provide the necessary infrastructure but remain abstracted away from the higher-level logic.

This architecture cleanly separates interfaces, execution, conversation state, capabilities, and infrastructure, which is why the system scales across multiple environments while staying consistent.

The Query Loop

At the core is a simple loop that runs every time a message is sent:

build prompt → call model → stream response

If the model decides it needs a tool (read files, run commands, etc.), the system executes it, adds the result back into the conversation, and repeats the loop. This continues until the model decides it’s done.

This forms a think → act → observe loop (ReAct), which is what turns it into an agent rather than just a chatbot.

The system uses async function*, so responses stream token by token as they’re generated.

This means no waiting for full responses, no callback complexity, and easy interruption.

Context Management: Compaction

To handle context limits, the system uses multiple strategies:

  • microCompact → trims large outputs per step
  • apiMicrocompact → server-side trimming
  • autoCompact → summarizes when context gets too large
  • sessionMemoryCompact → smarter, memory-based compaction
  • compact → manual full compression

Instead of one solution, it uses layered compaction to stay within limits.

Compaction sometimes failed repeatedly, leading to thousands of wasted retries per session.

The code comments tell the story directly: Around 1300 sessions were making up to 3000+ retries each, resulting in around 250,000 wasted API calls per day globally.

Fix: after 3 consecutive failures, it stops trying. A simple circuit breaker that prevents runaway API usage.

Memory Architecture (My Favorite Part)

How Claude “Dreams” to Remember

Claude doesn’t store everything in real time. Instead, it uses a background system called autoDream to periodically process and organize memory.

autoDream runs only when certain conditions are met: enough time has passed (24 hours), enough activity has occurred (5+ sessions), and no other autoDream process is running. This gating ensures expensive operations only run when necessary.

When triggered, autoDream launches a separate background agent. This isn’t just a function call, it’s an independent Claude session that runs silently while the user continues working. It’s also restricted to read-only bash commands (ls, grep, cat), it can explore the system, but cannot modify it directly.

AutoDream is not officially released yet. It is technically available. you just have to find it. Run /memory in any Claude Code session and look for the Auto-dream toggle. If it shows up, you can enable it right now.

The 4-Phase Memory Cycle

The process follows a structured cycle:

  • Orient → scan existing memory and understand current state
  • Gather → identify new or relevant information from recent activity
  • Consolidate → merge updates, remove outdated or conflicting data
  • Prune → keep memory compact, maintain a small index

When it finishes, a quiet “Improved memory” note appears in the transcript showing which files were updated.

Memory as a Hint, Not Truth

Memory is treated as a hint, not a source of truth. The system explicitly verifies stored information against the actual codebase before trusting it. If a memory contradicts reality, it gets deleted, not preserved.

Filesystem as State

Instead of a traditional database, the system uses the filesystem itself. Memory is stored as files, with timestamps tracking when consolidation last happened, and a lock file preventing simultaneous runs. If a process crashes, the system detects a stale lock and safely recovers.

This design avoids storing everything blindly. It batches, filters, and maintains memory over time, keeping it useful, compact, and reliable.

From Reactive to Proactive (Anthropic Roadmap)

One of the more interesting signals in the codebase is a system referred to as KAIROS, which appears to be gated behind feature flags and not exposed to users.

While details are limited, it suggests a shift in direction.

Today, the system is reactive, it responds when you ask.

KAIROS hints at something different: a system that can run in the background, observe changes, and act within predefined boundaries without constant prompting.

Instead of repeatedly issuing commands, the user defines intent — and the system takes care of execution.

It’s a move from “tools you use” to “systems that work for you.”

Anti-Distillation: Defensive Design

In claude.ts, there appears to be a flag related to anti-distillation. When enabled, additional tool definitions may be injected into the system prompt.

One possible interpretation is that this makes it harder to infer real tool usage patterns purely from API traces.

The system isn’t just designed to use tools — it’s designed to make that usage harder to replicate externally.

Prompt Caching: Where the Cost Actually Drops

Every API call has a cost, but not every part of the prompt needs to be reprocessed each time.

The system is designed to separate what changes from what doesn’t.

  • The stable parts (system prompt, tools, core instructions) stay identical
  • The variable part (latest message) is the only thing that changes

Because of this, the stable portion gets cached, and only the new input is processed fresh.

What leaked was the source code around the model, not the model itself.

The exposure includes the scaffolding, how the system structures prompts, manages tools, and orchestrates agents. But the core components that make the model intelligent are absent.

The model weights, training data, and underlying research are not part of runtime code. They are never bundled into client-side artifacts like .map files.

This wasn’t a model leak. It was a systems leak.
