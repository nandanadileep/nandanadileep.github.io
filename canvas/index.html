Weighted pseudorange and TDCP factors dynamically by satellite elevation angle and SNR, down-weighting low-horizon and weak-signal satellites in the information matrix rather than treating all measurements equally, which is where WLS fundamentally breaks in urban multipath environments.

Mycelium

The reliability layer for AI agents

  • 32K+ downloadsPyPI
  • Open sourceMIT licensed
  • Creator & maintainerMycelium runtime
ENGINEERING
The problem I’m solving

An agent can choose the right action and still produce the wrong outcome: a timeout can trigger a duplicate send, two workers can race to run the same tool, or a process can crash after the provider has already accepted a request. I built Mycelium to control this action boundary. It sits between an agent and its tools, validating proposed calls, coordinating execution, recording outcomes, and deciding what recovery is safe.

A stable identity for every action

A retry needs to refer to the same logical effect, rather than becoming a fresh action just because the model generated another tool call. Mycelium gives protected actions stable identities and records their lifecycle in a durable ledger. Completed actions can return their stored outcomes. In-flight or uncertain actions follow explicit coordination and recovery rules instead of blindly re-running the function body.

Validation before a tool runs

The runtime applies the checks configured for the tool and run before execution. These include argument validation, tool allowlists, permitted paths and destinations, sensitive information checks, current facts, and authorization scope. Time-bound permissions and destructive-action grants can be checked again at the action boundary. This makes the execution decision depend on current authority and policy, rather than relying only on an earlier model instruction.

Concurrency, leases, and fencing

Multiple workers can encounter the same action after retries, restarts, or concurrent scheduling. Mycelium coordinates claims through durable storage, using leases and fencing to control which worker owns execution and which state transitions remain valid. Action identity, claims, execution ownership, and outcome recording belong to the runtime, so individual clients do not each implement their own competing interpretation of the safety rules.

Recovery based on evidence

A failed request does not prove that its external effect failed. Mycelium distinguishes a known pre-effect failure from an attempt whose provider outcome is ambiguous. Depending on the evidence and effect classification, it can return a stored result, wait, reconcile the provider outcome, or stop safely. Another execution requires a truthful NOT_EXECUTED verdict; uncertainty is not permission to retry. The guarantee depends on the protected boundary and provider evidence, rather than promising universal exactly-once delivery.

Recovering multi-step operations

For supported sequential Python functions, an outer composite decorator coordinates child calls that are already ledgered. Completed children replay stored results, while unfinished work proceeds under a durable parent lease and fence. Definition drift, uncertain child outcomes, and lost parent authority block unsafe progression. Local parent recovery supports file and SQLite storage; Redis and PostgreSQL support shared parent control across workers. The wrapper does not discover hidden provider calls or make arbitrary Python control flow recoverable.

Controlling the whole run

Reliability also means knowing when to stop. Mycelium can detect repeated action loops and enforce time, step, token, and cost budgets. It validates message, history, and state before the next action, and can refuse a completion claim while required work remains open. These controls complement the action ledger: the system checks both whether an individual call may run and whether the surrounding agent run is still making valid progress.

Python and language-neutral integrations

Python applications can integrate through YAML configuration, decorators, or a manual API, including workflows built with LangGraph and CrewAI. Other runtimes use an authenticated HTTP/JSON sidecar backed by the same Python engine. Experimental TypeScript and Go clients use that protocol without reimplementing action identity, leases, fencing, or recovery. The v1alpha1 sidecar protocol remains a development contract; Python composite recovery is not exposed through the sidecar.

Storage and deployment choices

File and SQLite storage support durable local operation. Redis and PostgreSQL support shared workers when configured with the durability the application needs. The explicit shared PostgreSQL sidecar profile includes pooled connections, health and readiness probes, overlapping token files for rotation, and Docker Compose examples. These options keep the same execution model usable from a local application through a deployment with multiple cooperating workers.

Auditable recovery and operator authority

Mycelium records decisions and durable outcomes, with optional signed receipts. Operator releases can require a signed capability scoped to the operator, request, effect, tool, tenant, resolution, and policy version. Validity checks and durable single-use nonces reject tampering and replay. A trusted host control plane issues the capability, and the operator still verifies the provider outcome before releasing an uncertain action.

Making integration verifiable

The CLI provides init, demo, and configuration-driven execution. The bundled setup skill helps inventory tools and wire the runtime boundary. Doctor inspects configuration; Verify exercises synthetic crashes, retries, concurrency, storage failures, recovery, and guardrails. Repository checks also cover installed packages, cross-language conformance, and reproducible distribution builds. These checks validate the configured integration and implementation; they do not prove that a real external provider always behaves correctly.

The boundary of the guarantee

Only calls routed through Mycelium are protected. A ledgered transition must correspond to an independently observable and reconcilable effect; an opaque function hiding several effects needs explicit child boundaries or provider instrumentation. Storage durability, truthful effect classification, stable host-owned identities, and reliable provider evidence all matter. I designed Mycelium to stop when the evidence is insufficient, instead of concealing ambiguity behind an optimistic retry.

tiny-reranker

Inference performance, custom GPU kernels, and serving experiments

13 experiments across two hardware environments.

ENGINEERING
What I built

Ran a systematic inference-performance study on cross-encoder/ms-marco-MiniLM-L6-v2, a pretrained reranker with about 22.7 million parameters. Compared PyTorch, MLX, compilation, custom Metal/CUDA/Triton kernels, batching, and Python/Rust HTTP coordination on Apple M5 and NVIDIA L40S. Kept pretrained weights unchanged so the study measured execution choices rather than model training.

Three levels of performance

Separated individual GPU operation timing, complete document scoring, and complete HTTP requests. Direct scoring includes tokenization, input transfer, the model forward pass, and returning CPU-readable scores. HTTP also includes request handling, queueing, sorting, and serialization. A faster operation did not automatically count as a faster model or service.

Workload and correctness contract

Fixed the primary workload at 100 documents per query, pair batch size 16, FP32, and a 512-token maximum. Used unmodified BM25 candidates from SciFact and NFCorpus rather than injecting positive documents. The accuracy audit covered 485 queries at 10, 50, and 100 candidates: 77,600 query–document pair occurrences per implementation. All 11 implementation audits passed the declared numerical and ranking checks, with no top-1 or top-10 membership changes.

Repeated measurements and practical decisions

Collected 18 paired primary repetitions across six Apple sessions and 15 across five NVIDIA sessions. Used session-level exploratory 95% intervals and a predefined practical selection rule: the lower interval bound had to exceed a 5% gain. This separated a small measurable difference from a result large enough to justify an implementation change.

PyTorch versus MLX

On Apple M5, stock PyTorch scored 87.4 pairs/second versus 40.7 for MLX in the warm primary direct-scoring workload. The installed MLX fused full-attention kernel did not support this model’s 32-wide heads; dispatch evidence and runtime checks established a mathematical fallback. The comparison describes these implementations and this workload, rather than a universal framework ranking.

Compilation: where it helped

torch.compile delivered a paired 13.7% warm direct-scoring gain on Apple M5, with an 8.1%–19.8% exploratory interval. Compiled MLX improved its own direct-scoring baseline by 25.3%, with a 13.9%–37.9% interval. On L40S, compiled PyTorch scored 736.8 pairs/second versus 712.4 stock, a paired 3.3% gain that did not clear the predefined practical threshold.

Custom Metal: faster operation, no established model gain

Implemented a fused residual-addition and LayerNorm kernel for hidden size 384 and validated it on synthetic inputs and real model activations. The isolated Metal operation improved by roughly 1.38×–1.50× across the tested shapes. However, the custom-versus-native model-scoring comparisons included parity. That distinction is the central finding: an isolated kernel improvement was insufficient evidence for adopting a new end-to-end inference path.

Custom CUDA and Triton

Implemented the same fusion in CUDA and Triton on NVIDIA L40S. Both passed the accuracy audit, but neither beat compiled stock PyTorch in the primary direct-scoring comparison. Operation results varied by tensor shape. A selected-query profile placed LayerNorm at about 1.9% of summed leaf GPU-kernel time; this helped interpret the intervention without treating one profile as a universal bottleneck breakdown.

Batch size, request size, and context length

Varied pair batch sizes 1/8/16/32/64, documents per request 10/50/100, and token caps 128/256/512 separately. NVIDIA benefited from larger batches in the diagnostic sweep; Apple results were non-monotonic. Shorter contexts were faster but truncated inputs, and the separate quality diagnostic did not establish application equivalence. Retained the frozen batch-16, length-512 workload for primary comparisons.

Python and Rust serving

Compared Python and Rust coordinators around the same Python inference worker, with matched validation, sorting, response contents, and timeouts. Some Rust/PyTorch intervals favored Rust by roughly 2–4%, but none cleared the practical 5% criterion. The study did not establish a reason to switch languages for throughput. Rust changed coordination, not the underlying model implementation.

Concurrency and queueing

With one inference worker and no cross-request batching, raising concurrency from one to four to eight mostly increased queueing. For Python/PyTorch at 100 documents per request, median latency rose from about 0.762 seconds to 2.997 and 5.917 seconds, while throughput stayed near 1.32 requests/second. At concurrency four, queue wait was about 2.240 seconds versus 0.755 seconds of processing.

Did direct-scoring gains survive HTTP?

Ran matched follow-up service comparisons rather than borrowing earlier baseline measurements. Compiled PyTorch’s Apple direct-scoring gain did not become a practical HTTP gain. Compiled MLX improved its own HTTP baseline, with paired gains of 11.2%, 10.0%, and 15.7% at concurrency one, four, and eight; only one and eight cleared the practical criterion. MLX still remained slower than PyTorch in those matched service measurements.

Startup cost and amortization

Measured stock versus compiled first scoring at 0.51 versus 7.68 seconds on Apple, and 0.46 versus 24.74 seconds on NVIDIA. These were single ordered startup pairs with fresh software-cache directories, not fully cold-start distributions. Illustrative amortization estimates were about 41 K100 queries on Apple and 11,287 on NVIDIA; they are not production break-even predictions or evidence of an HTTP break-even point.

Validation and reproducibility

All 12,288 accepted HTTP responses passed score and ranking validation, with no measured failures or timeouts in those accepted runs. Retained the frozen protocol, measured tables, source and artifact hashes, accuracy contracts, test fixtures, and reproduction instructions. Archived earlier training history separately so the inference study is not confused with the experimental 4.7M scratch model.

What the findings support

For this workload, compiled PyTorch was the practical Apple warm direct-scoring choice; compiled MLX improved its own backend; custom kernels and a Rust coordinator did not establish a practical application advantage. HTTP used Apple local loopback and closed-loop load. NVIDIA HTTP, mixed precision, open-loop overload, distributed serving, and cross-request batching were not measured. The engineering outcome is a reproducible way to decide which optimizations are worth keeping.

LLM serving with MLX

An experimental inference server for Apple Silicon.

A serving stack small enough to inspect

Built a compact MLX inference server to study the systems behind LLM serving on a Mac: request scheduling, cache management, generation, and streaming. It runs real inference, with a quantized Llama 3.2 1B model as the default, behind FastAPI endpoints. The project is an experimental learning and benchmarking system inspired by vLLM.

Scheduling and generation

Implemented experiments with continuous batching and configurable chunked prefill, including an optional long-lived batch generator for continuous request admission. Native generation endpoints and an OpenAI-compatible chat-completions endpoint support server-sent event streaming, letting clients receive tokens while generation is in progress.

KV caches and decoding

Added exact and shared-prefix KV-cache reuse, a paged block-pool simulation with allocation and fragmentation metrics, and an optional gathered KV backing store. The gathered representation is rematerialized for dense attention; it is not a fused paged-attention kernel. Optional speculative decoding uses a configurable draft model and draft-token count.

Observability and reproducible comparisons

Exposed metrics for time to first token, queueing, cache hits, blocks, tokens, and memory. Included load tests and plots comparing the MLX server with vLLM on a Colab GPU and llama.cpp on CPU. The harness records average and tail latency, request throughput, token throughput, and memory across concurrency levels. Results are hardware- and configuration-specific snapshots, not universal speed claims.

Scope

Designed for single-machine experiments. The project does not implement CUDA kernels, fused device-level paged attention, tensor parallelism, pipeline parallelism, or the production scheduler found in vLLM.

nanoLLM

Swapped Every Part of nanoGPT With Modern Alternatives.

A controlled architecture experiment

Extended Karpathy’s nanoGPT into a configurable experimental model named nanoLLaMA. Added RMSNorm, SwiGLU, rotary position embeddings, grouped-query attention, multi-head latent attention, mixture-of-experts routing, and multi-token prediction. Each component can be switched independently through configuration or the CLI.

Keeping comparisons consistent

Benchmarked changes on Shakespeare character-level data with four layers, four heads, a 128-dimensional embedding, 2,000 CPU training iterations, and the same seed. Validation loss uses next-token cross-entropy without training-only auxiliary losses, making the reported comparisons easier to interpret.

Quality and memory tradeoffs

The README reports a baseline validation loss of 1.6645 and 1.5259 for the combined stack. In the same small setup, GQA uses a 2× smaller KV cache with some quality cost, while MLA uses an 8× smaller KV cache with a larger quality cost. These results document the tradeoffs in this experiment rather than extrapolating to large-scale models.

What the experiment shows

The combined configuration reaches the baseline’s final validation loss by step 500 in the recorded run. The project makes architecture choices inspectable and measurable: normalization, position encoding, attention memory, sparse routing, and training objectives can be studied separately before combining them.

Auto-Agent

A repository observer with presence-aware notifications and persistent memory

Observe, remember, and nudge

Built an open-source background agent that checks a repository every five minutes for TODOs, stale pull requests, missing environment keys, and recent code changes. The documented agent observes and nudges; it does not edit source code.

Context and delivery

Each cycle assembles git history, modified files across ten language extensions, TODOs, open pull requests, and memory topics. Machine-idle detection influences the autonomy level and how findings are delivered: a desktop notification when away, or a quiet terminal update when present. Actions are logged and deduplicated per day.

Memory across sessions

The nightly AutoDream pass consolidates the day’s observations into persistent topic memory. Subsequent cycles can use that context rather than starting from scratch, connecting repository events across work sessions.

Implementation

Used Python, APScheduler with AsyncIO, watchfiles, PyGithub, SQLite, and a FastAPI dashboard. Groq supports regular observation cycles; Gemini supports nightly consolidation, with Ollama available for local models. The repository also includes optional webhook-tunnel and notification integrations.

Some beliefs leave slowly

+

Recently, while reading Maxwell Maltz's Psycho-Cybernetics, I came across a passage from Bertrand Russell's The Conquest of Happiness.

Russell's point is simple: sometimes reason has already rejected a belief, but the rest of us has not. An old fear, guilt, or idea can still return automatically and feel true.

“Whenever it thrusts foolish thoughts or feelings into your consciousness, pull them up by the roots, examine them, and reject them.”

When that happens, look at the belief, ask where it came from, and remind yourself clearly what you actually believe now. Keep doing this until the newer belief reaches deeper than the old one.

I have been thinking about this lately. Knowing that something is irrational once is not always enough. Sometimes we have to reason with ourselves again and again, until we stop living by a belief we no longer hold.

Bertrand Russell, The Conquest of Happiness (1930), Chapter 7: “The Sense of Sin.”

Why 698³ behaves exactly like 5³

+

I was bored and had no phone with me, so pardon me.

I noticed something weird about digit sums of cubes:

1³ = 1      → 1
2³ = 8      → 8
3³ = 27     → 9
4³ = 64     → 1
5³ = 125    → 8
6³ = 216    → 9
7³ = 343    → 1
8³ = 512    → 8
9³ = 729    → 9
10³ = 1,000 → 1

Only 1, 8, 9. Over and over. Why would cubes be so picky?

When I looked into it, I realized I shouldn't be surprised. Something obvious is happening.

Every number is built from powers of 10. Like 347 = 3×100 + 4×10 + 7. But in the world of remainders mod 9, the number 10 behaves exactly like 1. So does 100, 1000, 10000...

That means 347 mod 9 acts like 3 + 4 + 7 mod 9. Which is just the digit sum. Adding digits is literally just taking remainders mod 9.

347 % 9              = 5
3 + 4 + 7 = 14 → 1+4 = 5

So what do cubes produce mod 9? Every number is either a multiple of 3, or it isn't. If n = 3k, then n³ = 27k³, which is 0 mod 9. For everything else (1, 2, 4, 5, 7, 8), their cubes mod 9 cycle through just 1 and 8.

Cubes don't choose 0, 1, 8. They have no other option.

Now take 698. Its digit sum is 6 + 9 + 8 = 23 → 2 + 3 = 5. So 698 behaves like 5 mod 9. Which means 698³ behaves exactly like 5³.

Try any number. Same thing.

Why is this world literally small?

+

I was thinking about this the other day and it messed me up a little.

The claim is: you can reach any person on the planet through at most 6 people. You to a friend, to a friend, to a friend... six hops and you personally know Max Verstappen or Jon Hamm.

Sounds insane. But let's actually think about it.

Say you know 100 people. Those 100 know 100 people. That's 10,000 at 2 hops. At 3 hops: 1,000,000. At 4: 100,000,000. At 5: 10,000,000,000. That's already more than the world's population. And we only used 5.

So mathematically? Yeah. Totally believable.

But hold on. Math is cheating a little. The assumption here is that every hop is a fresh person. In reality, your friend group overlaps a lot. Your college friends know each other. Your work people know each other. So the 100 to 10,000 step is optimistic.

So the real question becomes: how clustered are human social networks?

And this is where it gets interesting. Human networks are "small worlds": highly clustered locally, but with a few random long-range connections that act like shortcuts. Those shortcuts collapse the degrees dramatically.

Think of it like this. India and the US feel socially far. But one person who studied abroad just bridges the whole thing. One hop and suddenly two massive clusters are connected.

The real number apparently varies between 3 and 7 depending on the study. Facebook found it was 3.5 on average in 2016.

3.5 hops. You're not that far from anyone.
