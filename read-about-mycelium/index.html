Mycelium: Turning AI Agents into Reliable Systems

A model can make the right decision and still produce the wrong real-world result. Reliability begins at the moment an agent's intent becomes an external effect.

By Nandana Dileep August 30, 2026 14 minute read

In this essay The gap Architecture Identity Durable state Recovery Reconciliation Guardrails Evidence Adoption Boundaries

AI agents increasingly use tools to send messages, update records, modify cloud resources, and more. Once an agent crosses that tool boundary, its decision becomes a real-world effect.

A lot can go wrong there. A worker can crash after a provider accepts a request but before the result is recorded. The same logical action can arrive again under a different dispatch ID. Arguments can change between retries. Two workers can race. An agent can exceed its scope or budget, target the wrong destination, leak a secret in tool arguments, or finish without durable evidence of what happened.

I built Mycelium as a reliability and control layer for these consequential calls. It gives each protected action a stable identity, records its lifecycle durably, coordinates competing workers with leases and fencing, classifies side effects, and decides whether a call may execute, must wait, can return a stored result, needs provider reconciliation, or must stop safely.

The goal is not to make a model infallible. It is to make protected actions traceable, bounded, recoverable, and honest about what the system knows.
01 · The reliability gap

Prompts can suggest behavior. They cannot enforce execution.

Instructions such as “never charge twice,” “only modify this repository,” or “stop after four attempts” can guide a model. They cannot atomically coordinate a provider request, a process crash, a durable write, and a replacement worker.

Here are two examples of how that gap appears in practice.

Example 1: an uncertain payment

  1. A worker records that it plans to charge order 42.
  2. It sends the request to the payment provider.
  3. The provider creates the charge.
  4. The worker loses its connection or dies before recording success.
  5. Another worker receives the same logical request.

At step five, “retry” is not a safe default. The system needs to distinguish three facts: the provider completed the effect, the provider definitely did not execute it, or the provider cannot yet say. Pretending the third state is either success or failure is how duplicate charges and missing work enter production.

Mycelium preserves that uncertainty instead of erasing it:

Intended→Attempting→CommittedorAbortedorUnknown

An ambiguous mutation is not blindly repeated. Depending on its classification and the available evidence, Mycelium can return a stored result, wait for an active owner, reconcile with the provider, authorize one proven-safe attempt, or stop for operator resolution.

Example 2: an unauthorized destination

Now consider a support agent allowed to send messages only to approved customer domains. It tries to send one to an unapproved address. Nothing crashed, and nothing is being retried. The proposed action is simply outside its declared destination boundary.

With a destination guard configured, Mycelium rejects the call before it creates a ledger claim or reaches the tool body. Reliability here means preventing an unauthorized effect, not deduplicating one.

Together, these examples show two sides of Mycelium's role: recovering safely when an outcome becomes uncertain and preventing a consequential action that should not begin.

02 · Architecture

A protected call becomes a protocol, not a bare function invocation.

Configuration determines which tools are protected, how their effects are classified, which storage backend records them, and which guards apply. Mycelium composes those protections around the registered callable.

When a call arrives, outer guards such as loop, budget, scope, and state authority can reject it before a claim exists. If they pass, Mycelium derives the effect identity and atomically claims its ledger record. The resolution gate can return an existing result, wait for another worker, permit a new attempt, or stop for reconciliation or operator review.

Before an allowed body runs, applicable use-time, destructive, destination, and secret policies become one fenced decision. A denial records ABORTED; the body never runs. After execution begins, the declared side-effect boundary decides whether failure is known to be pre-effect or must remain UNKNOWN.

03 · Identity

What counts as the same real-world action?

A replacement worker may have a new process ID, dispatch ID, or framework tool-call ID while continuing the same business operation. Mycelium needs to recognize that “charge order 42 for the approved amount” on worker two is the action worker one already started.

For each protected consequential call, Mycelium derives a deterministic effect_id from stable scope, tool, canonical arguments, destination, side-effect classification, agent, and policy version. A new physical dispatch can resolve to the existing logical effect rather than creating an unrelated record.

That identity does more than deduplicate. It lets Mycelium coordinate competing workers, return a stored result, detect unsafe changes, reconcile an uncertain provider outcome, require provider-key reuse, and attach evidence to the right operation.

Mycelium relies on the application to identify each action consistently. Too little information can make different actions look the same. Changing information between retries can make the same action look different.

Mycelium also checks that an action has not changed between retries. If a retry changes an important detail, such as the payment amount, Mycelium blocks it. Applications should identify actions using stable information, such as an order ID, rather than temporary IDs created for each retry.

04 · Durable state

Who owns the action, and could the effect have begun?

Once Mycelium recognizes an action, it needs durable answers to two questions: which worker currently owns it, and could the external effect already have happened? The ActionLedger is authoritative for both. It stores identity and arguments, owner, lease and fence, boundary state, provider reference, result, policy decision, outcome, and operator resolution.

The backend determines where that memory survives:

  • Memory is useful for tests but disappears with the process.
  • File and SQLite provide durable single-node storage.
  • Redis and PostgreSQL support shared multi-worker deployments when configured with the durability the application requires.

Mycelium temporarily assigns each action to one worker. If another worker takes over, the old worker can no longer update the result, even if it starts running again. Mycelium also does not treat an expired time limit alone as proof that the worker stopped.

The application also marks where an external request begins. If something fails before that point, Mycelium knows the external action did not start. If it fails after that point, the provider may already have received or completed the request, so Mycelium treats the outcome as uncertain instead of retrying blindly.

from mycelium import (
    SideEffectClass, ToolTransitionBinding,
    ledger_sync, side_effect,
)

binding = ToolTransitionBinding.for_tool(
    agent_id="billing-agent",
    policy_version="2026-08-1",
    side_effect_class=SideEffectClass.NON_IDEMPOTENT_MUTATE,
    request_id_from="order_id",
)

@ledger_sync(storage=durable_ledger, transition_binding=binding)
def charge_order(order_id: str, amount_cents: int):
    with side_effect():
        return payment_gateway.charge(order_id, amount_cents)

This is intentionally small. A production integration still needs correct scope, durable storage, truthful provider reconciliation or supported idempotency, secret handling, and application tests. A direct provider call that bypasses every protected boundary remains outside Mycelium's control.

05 · Recovery semantics

Recovery depends on the effect and the evidence.

After an interrupted call, there is no correct universal retry rule. Mycelium needs to know both what repeating the operation would do and what evidence exists about the first attempt.

What would a repeat do?

  • A read creates no external mutation and can normally be repeated.
  • An idempotent mutation sets a resource to the same intended state when repeated.
  • A keyed mutation is safe only when the provider receives the same valid idempotency key.
  • A non-idempotent mutation creates another effect, such as another message, charge, or record.
  • An irreversible action cannot be safely undone and needs the most conservative handling.

How can we know what happened?

  • An idempotent operation may permit a policy-controlled repeat.
  • A queryable operation has a trustworthy read-only provider lookup for this specific effect.
  • A blind operation has no reliable way to determine its outcome.

Mycelium combines those answers with boundary state. It may return a stored result, safely repeat an idempotent operation, reuse a valid provider key, reconcile through a read-only lookup, authorize one attempt after confirmed non-execution, or hard-block when uncertainty remains.

Reading inventory may be repeatable. Setting a CRM field to an exact value may be idempotent. Creating a payment may be safe only with the same provider key. Sending a message may produce a duplicate. Deleting a record may be irreversible. The business domain does not decide the classification; the provider operation's real behavior does.

06 · Reconciliation

When the answer is unclear, ask what happened.

When an action becomes UNKNOWN, Mycelium does not assume failure and blindly repeat it. If the application recorded a provider operation reference, a registered read-only reconciler can ask the provider.

Completed

Record and return the provider-confirmed result. Do not run the tool again.

Not executed

Perform a fenced reset that can authorize one execution.

Unknown

Keep the action blocked. Missing evidence is not permission.

Timeouts, outages, lookup errors, and missing references also fail closed. A provider-conformance kit can test whether an adapter behaves conservatively, but it cannot prove that deployed credentials are read-only or that a third-party API is complete. During indexing delay, zero matches should normally remain UNKNOWN, not become NOT_EXECUTED.

If automated proof is unavailable, an authorized operator can resolve the transition. Mycelium records that decision instead of erasing history, and a “not executed” resolution grants only one new attempt. An OperatorAuthorizer can enforce host authentication; a CLI --by label is audit context, not identity proof.

07 · Guardrails

Guardrails control what can run and when work is complete.

The ledger tracks each external action. Other controls decide whether a proposed action is allowed and whether the agent can report that its work is finished.

  • Outer scope, state-authority, loop, and budget guards can stop a call before it creates a ledger claim.
  • For a ledger-backed consequential tool, destination, destructive, secret, authority, and use-time facts join the fenced atomic decision before the body runs. Time-sensitive authority is checked again at the final use boundary.
  • Completion contracts prevent supported terminal paths from reporting success while required work is still pending.

These controls are opt-in and depend on evidence from the host. YAML cannot protect a callable that bypasses its wrapper, and Mycelium cannot invent destination authority or business permissions. Secret references reduce accidental exposure in configuration and evidence, but no wrapper can protect a value after application code resolves and logs it.

08 · Evidence

Records and checks show what happened.

Mycelium keeps a durable record of each protected action. It also creates monitoring events that help developers understand completed actions, failures, blocked calls, worker conflicts, and unexpected repeated executions.

If required monitoring information cannot be saved, Mycelium reports an error instead of hiding the problem. That error cannot undo an external action that already happened, so teams should monitor it. The records can also be inspected or exported for operations and audits.

Doctor checks; Verify tests

Doctor · Setup check

Checks the configuration, registered tools, and optional connections. It does not run real tools or call an LLM.

Verify · Safe simulations

Runs isolated tests of crashes, retries, concurrent workers, storage failures, recovery, and guardrails without touching real business systems.

These checks show whether the tested setup behaves as expected. They cannot prove that production permissions are correct or that an external provider will always return accurate information.

$ mycelium doctor --config mycelium.yaml --strict
$ mycelium verify --config mycelium.yaml --scenario all --strict
$ python -m pytest sdk/tests -q
09 · Adoption

Begin with one consequential boundary.

Start with one external mutation whose duplicate, wrong destination, or uncertain outcome would matter:

Using an AI coding agent? After installing mycelium-runtime, run mycelium skills install, then ask the agent: “Set up Mycelium in this project.” The official setup skill guides the agent through inspecting the project, finding consequential tool boundaries, creating or merging the configuration, wiring the integration, adding tests, and running Doctor and Verify. It completes what the code can prove and asks for anything it cannot safely infer, such as a business identity, production credentials, permissions, or provider guarantees.

  1. Install the released mycelium-runtime package and use the documentation for that release.
  2. Give the operation a stable, host-owned business identity.
  3. Classify its effect and recovery capability truthfully.
  4. Choose storage that matches the deployment topology.
  5. Route the real provider call through a wrapper or supported integration.
  6. Add a provider key or read-only reconciler only when the provider truly supports it.
  7. Add the necessary guards, then run application tests, Doctor, and Verify.

Versioned YAML, JSON Schema, generated configuration reference, and CLI templates make those choices reviewable. They cannot supply business identity, credentials, permissions, or provider truth for the application.

10 · Guarantees and boundaries

The limitations are part of the guarantee.

For one stable protected effect identity, Mycelium permits one initial winning attempt. Another body execution requires a consumed, truthful NOT_EXECUTED verdict proving the earlier attempt created no external effect. This supports an at-most-once external-effect guarantee under the documented protocol. It is not universal provider-level exactly-once delivery.

The guarantee depends on every consequential call crossing the protected boundary, complete host-owned identity, truthful classification and provider evidence, and storage whose atomicity and durability fit the deployment. A wrong reconciler verdict, incomplete identity, bypassed wrapper, or unsuitable backend invalidates the premise.

Mycelium does not automatically observe an agent CLI's internal messages and tool calls or discover every network request in arbitrary code. Calls must pass through a wrapper, registered callable, supported framework or client integration, or another controlled boundary. Broader automatic discovery is later scope.

One ledgered transition represents one independently observable and reconcilable effect. If one opaque function hides several unrelated effects, Mycelium cannot infer which internal steps succeeded after a crash. Explicit child boundaries or provider/client instrumentation can expose them; unchanged-function composite recovery is later scope.

Saying UNKNOWN when evidence is missing is safer than silently turning an assumption into permission.

A consequential agent action should not be a bare function call surrounded by hope. It should have stable identity, current authorization, durable intent, a fenced owner, an observable effect boundary, a terminal state, outcome evidence, and a recovery path based on proof.
